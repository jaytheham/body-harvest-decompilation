# Alias in `symbol_addrs.us.txt` hijacks splat naming → clean build link error

## Symptom

Local builds pass, but a **fresh extract** (CI) fails to link a C file:

```
mips-linux-gnu-ld: build/src.us/overlay_gameplay/outside/CFE30.c.o: in function `func_800C4274_D3224':
src.us/overlay_gameplay/outside/CFE30.c:1878: undefined reference to `D_80156EDA'
...
make: *** [Makefile:283: build/bh.us.elf] Error 1
```

Note the missing symbol is the **canonical** name (`D_80156EDA`), while the
newly added alias (`D_80156EDA_Draw`) links fine.

## Cause

A split read/write (or volatile) alias was added to the **wrong** symbol file:

```
symbol_addrs.us.txt:
    D_80156EDA_Draw = 0x80156EDA;
    D_80156EDA = 0x80156EDA;   // harmless-looking, but does NOT define anything for the linker
```

Two separate problems:

1. `symbol_addrs.us.txt` is **only read by splat**, never passed to the linker
   (`LD_FLAGS = -T bh.ld -T undefined_syms.us.txt -T undefined_syms_auto.txt`).
   So declaring a symbol there does **not** create a linker definition.

2. When splat has a user symbol at an address, `retrieve_symbol()` returns the
   **first** symbol registered at that address and labels every disassembly
   reference with it. The canonical auto-name (`D_80156EDA`) is then never
   "referenced", so `write_undefined_syms_auto()` omits it from the generated
   `undefined_syms_auto.txt`. C code using the canonical name fails to link.

## Fix

Keep the alias out of `symbol_addrs.us.txt` and define **both** names in the
tracked linker symbol file `undefined_syms.us.txt`:

```
undefined_syms.us.txt:
    /* Volatile read/write alias for func_800C927C_D822C (canonical D_80156EDA is auto-detected). */
    D_80156EDA_Draw = 0x80156EDA;
```

- The canonical `D_80156EDA` stays **auto-detected** (referenced in asm, not
  defined) and is regenerated into `undefined_syms_auto.txt` on every extract.
- The alias `D_80156EDA_Draw` is committed in `undefined_syms.us.txt`, so it
  exists even on a clean extract.
- Remove the `symbol_addrs.us.txt` entries, otherwise the canonical name is
  dropped from the auto file again.

This mirrors the existing aliases `D_963A70_2 = 0x00963A70` and
`D_80031260_31E60 = 0x80031260` in `undefined_syms.us.txt`.

## Detection rule

If a C-only alias resolves to a linker symbol that has **no committed
definition**, suspect this pattern. `grep` the auto file and `symbol_addrs.us.txt`
for the address — if the *canonical* name is missing from the auto file, an
`symbol_addrs.us.txt` entry at that address is hijacking splat's naming.

`undefined_syms_auto.txt` is gitignored and regenerated by `make extract`;
anything you add there by hand passes locally but is lost on a fresh extract.
